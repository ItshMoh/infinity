# Context compression, compaction, and the bottlenecks of long-context LLMs (state of evidence, Oct 2026)

Compiled 2026-10-18 by a research subagent. Every number below was read from the cited primary page unless marked **[secondary]** or **[unverified]**. Several widely-quoted figures turned out to be misattributed; those are flagged.

---

## PART A — The bottlenecks

### A1. Context rot: the actual curves

**Lost in the Middle (Liu et al., 2023)** — https://arxiv.org/html/2307.03172v3
20-document multi-doc QA, relevant doc moved through positions. GPT-3.5-Turbo: 75.8% (position 1) → 53.8% (middle) → 63.2% (end). Closed-book (no documents at all) = 56.1%, i.e. *a relevant document in the middle of 20 is worse than no documents*. Claude-1.3 was nearly flat (59.9/56.8/60.1). Key-value retrieval worst case 45.6% without query-aware contextualization.

**NoLiMa (Adobe, ICML 2025)** — https://arxiv.org/abs/2502.05167 · table: https://github.com/adobe-research/NoLiMa
Removes literal lexical overlap between question and needle, forcing a one-hop latent association. "Effective length" = longest context keeping ≥85% of the short-context base score.
- GPT-4.1 (1M claimed): effective 16K. 97.0 base → 84.9 @16K → 79.8 @32K → 69.7 @64K → 64.7 @128K.
- GPT-4o: effective 8K; 56.0 @128K. Claude 3.5 Sonnet: effective 4K; 29.8 @32K. Gemini 2.5 Flash (no thinking): effective 2K; 48.4 @32K. Llama 4 Maverick (1M claimed): effective 2K; 24.5 @32K.
- Reasoning models (o1/o3) help but "fail to fully mitigate... particularly in contexts exceeding 16K."
This is the single most important curve for a personal assistant: "what did I feel last Tuesday" is a NoLiMa-style latent-match query, not a literal needle.

**RULER (NVIDIA)** — https://github.com/NVIDIA/RULER
Threshold = Llama-2-7B at 4K (85.6). GPT-4-1106: effective 64K, 96.6 @4K → 81.2 @128K. Llama-3.1-70B: 66.6 @128K. Mistral-Large-2407: 23.7 @128K. Gemini-1.5-Pro and Jamba-1.5-large stay >94 at 128K. "Almost all models fall below the threshold before reaching the claimed context lengths."
**Misattribution warning:** many 2026 blogs quote "GPT-4.1 fell from 96.6% to 81.2% in Chroma's study". That pair is actually RULER's GPT-4-1106 row, not Chroma.

**Chroma "Context Rot" (14 Jul 2025, 18 models: Claude Opus 4/Sonnet 4, o3, GPT-4.1, Gemini 2.5 Pro, Qwen3…)** — https://www.trychroma.com/research/context-rot
- All models degrade with input length, even on trivially simple tasks; needle *position* had no notable effect (contra Lost-in-the-Middle).
- Lower needle–question embedding similarity ⇒ faster degradation with length.
- 1 distractor reduces performance; 4 reduce it further; Claude models had the lowest hallucination rates, GPT the highest.
- Shuffled haystacks performed *better* than coherent ones across all 18 models — coherent surrounding prose is more harmful than noise.
- LongMemEval: full prompt ≈113K tokens vs focused ≈300 tokens; all models significantly higher on focused; the gap was largest for Claude Opus 4/Sonnet 4, driven by abstentions.
- Repeated-words task: Opus 4 degraded slowest but refused 2.89%, refusals beginning near 2,500 words.
**[unverified]** Exact per-length accuracy percentages are only in the charts, not the page text; blog numbers like "30%+ drop" could not be confirmed.

**2026 follow-ups**
- *Classifier Context Rot* (Martin & Roger, May 2026) — https://arxiv.org/abs/2605.12366 : Opus 4.6, GPT-5.4, Gemini 3.1 as transcript monitors missed a dangerous action **2×–30× more often** when it followed ~800K tokens of benign activity. Periodic reminders partially help. Direct evidence that a long, boring history actively blinds the model.
- *llm-stats failure-focused eval* (3 Feb 2026) — https://llm-stats.com/blog/research/a-failure-focused-evaluation-of-frontier-models : MRCR accuracy Gemini-3-Pro 76.9%, GPT-5.2 71.5%. Failure rate by number of needles: 2→34.7%, 4→49.8%, 8→60.7% (+26 pp). By context size: 10–50K chars 36.9%, 100K+ 44.9% (+8 pp). **Needle count, not raw length, is the primary difficulty factor.**
- *LongCoT* (arXiv 2604.14140) — https://arxiv.org/abs/2604.14140 : 2,500 problems requiring tens–hundreds of thousands of reasoning tokens; GPT-5.2 9.8%, Gemini 3 Pro 6.1%, while each local step is tractable.
- *Mechanistic synthesis* (TMLS, Jun 2026) — https://www.tmls.nyc/research/context-rot-mechanistic : FLenQA reasoning accuracy 0.92→0.68 from ~250 to ~3,000 tokens with the task fixed; attention calibration recovers 6–15 pts mid-context. Mechanism: softmax must sum to 1, so irrelevant mass lands on attention sinks (~80% on token 1 in one production model) plus RoPE recency decay ⇒ "starved middle". Its SNR model mρ/(N−m) gives illustrative effective lengths ~10⁶ tokens for literal matches vs ~3×10⁴ for latent associations (illustrative, not fitted).
- Google's own long-context doc concedes multi-needle accuracy is lower than single-needle and recommends putting the query at the end — https://ai.google.dev/gemini-api/docs/long-context
- **[unverified]** A GitHub survey note claims Gemini 3.1 Pro / Opus 4.7 / GPT-5.5 score 100% on 1M single-needle but degrade on multi-hop; no primary source found.

**Net picture (retrieval vs reasoning):** literal single-needle retrieval is essentially solved to 1M. Latent-match retrieval has an effective length of 2–16K on NoLiMa even for frontier models. Reasoning over *many* relevant items degrades with item count (+26 pp failure 2→8 needles) and with distractor count far more than with raw length.

### A2. Cost and latency
- **KV-cache memory:** Llama-3.x-70B ≈0.31–0.33 MB/token in BF16 (2 × 80 layers × 8 KV heads × 128 dims × 2 bytes); 1M tokens ≈ 320 GB FP16 (≈4×80 GB GPUs before weights); FP8 halves it — https://inventivehq.com/blog/llm-kv-cache-vram-memory-cost , https://dev.to/jagmarques/kv-cache-memory-calculator-how-much-does-your-llm-actually-use-85n
- **Prefill dominates agents:** Manus reports input:output ≈ 100:1, so KV-cache hit rate is "the most important metric"; cached Sonnet input $0.30 vs $3.00/MTok — https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus
- **Anthropic caching (official, Oct 2026)** — https://platform.claude.com/docs/en/build-with-claude/prompt-caching : writes 1.25× (5-min TTL) or 2× (1-h); reads 0.1× by default, 0.05× on Opus 5.5/Sonnet 5.5, 0.025× on Fable 5.1/Mythos 5.1. Example: Opus 5.5 $4 in / $5 write / $0.20 read; Sonnet 5.5 $2 / $2.50 / $0.10; Haiku 5.5 $0.10 ≤100K but **$0.50 above 100K**. Minimum cacheable prefix 512–4,096 tokens by model; TTL 5 min refreshed on use; prefix hierarchy tools→system→messages (changing tools invalidates everything after); max 4 breakpoints, 20-block lookback.
- **OpenAI (official)** — https://developers.openai.com/api/docs/pricing : cached input = 0.1× (GPT-5.5 $5 → $0.50; GPT-5.4 $2.50 → $0.25). Long-context surcharge >272K input: GPT-5.5 $10 in / $1 cached / $45 out. No write fee except gpt-5.6 family (e.g. $5 write vs $4 input).
- **Gemini (official)** — https://ai.google.dev/gemini-api/docs/pricing : 3.1 Pro $2 in ≤200K, **$4 above 200K and the whole request is billed at the long rate**; cache read $0.20/$0.40; cache storage **$4.50 per M tokens per hour**. Flash 3.8: $0.75 in, $0.075 cached, $0.50/M/hr storage.
- **Why "put everything in context" still loses in 2026:** a 500K-token endless chat costs $2.00 per turn uncached on Opus 5.5 or Gemini 3.1 Pro; the cached-read price (~$0.10–0.20/turn) only holds while the prefix is byte-identical and the 5-min TTL hasn't lapsed — every idle gap >5 min is a full 1.25× re-write ($2.50), and keeping 500K warm on Gemini costs $2.25/hour in storage alone. On top of that the model is operating in the NoLiMa regime above (effective length 2–16K for latent queries). Latency: all providers say TTFT grows with prompt length; **[unverified]** no measured 1M-token TTFT from a 2025–26 primary benchmark was found (one vendor blog cites ~30 s; Artificial Analysis measures at 10K-token inputs only).

### A3. Irrelevant context actively hurts
- GSM-IC (Shi et al., ICML 2023) — https://arxiv.org/abs/2302.00093 : accuracy "dramatically decreased" with one irrelevant sentence even on problems the model otherwise solves; mitigations: self-consistency and an explicit "ignore irrelevant info" instruction (effect sizes only in the PDF).
- GSM-DC (EMNLP 2025) — https://arxiv.org/html/2505.18761v2 : at reasoning depth 5, step accuracy Grok-3-Beta 43% → 19% and GPT-4.1 26% → 2% going from 1 to 15 distractors; a clean-trained Llama-3.2-1B fell 81.95% → 35.91% with distractors. Distractors corrupt *path selection*, not just arithmetic.
- Chroma: semantically similar-but-wrong content is the worst distractor; coherent prose worse than shuffled.
- Pitfalls of KV-cache compression (ACL 2026) — https://arxiv.org/abs/2510.00231 : under eviction, some instructions "degrade much more rapidly… effectively causing them to be completely ignored" (system-prompt leakage case study).
- Manus "few-shot ruts": agents imitate patterns present in their own history, drifting after ~20 similar items.

### A4. Retrieval bottlenecks
- **Negation:** embedding models map affirmative and negated text to near-identical vectors (vision-language — https://arxiv.org/pdf/2501.09425 ; intent encoders — https://arxiv.org/pdf/2403.04314 ; audio — https://arxiv.org/pdf/2607.12290). "Python code without dependencies" retrieves all Python code.
- **Temporal:** embeddings do not encode order or date; standard fix is extracting time entities into metadata filters. LongMemEval — https://arxiv.org/abs/2410.10813 — reports commercial assistants and long-context LLMs lose ~30% accuracy over sustained interaction and finds three design levers: session decomposition, fact-augmented key expansion, **time-aware query expansion**. Mem0's paper — https://arxiv.org/html/2504.19413v1 — shows OpenAI memory at 21.71 on temporal questions "attributed to missing timestamps in its generated memories" vs 55.51 for Mem0 with timestamps.
- **Multi-hop / multi-session is the hardest category everywhere:** Mem0 multi-hop 51.15 (lowest category); Mastra reports an apparent ~87% ceiling on LongMemEval multi-session — https://mastra.ai/research/observational-memory
- **Entity granularity:** "Dense Retrievers Can Fail on Simple Queries" — https://arxiv.org/html/2506.08592v1 — encoders fail on fine-grained entity/event matching; the paper calls it the embedding analogue of needle-in-a-haystack. **[unverified]** The exact phrase "needle-in-a-needlestack" surfaced no primary source; the closest evidence is this paper plus the llm-stats multi-needle result.
- **Chunk context loss:** Anthropic contextual retrieval — https://www.anthropic.com/engineering/contextual-retrieval — top-20 failure 5.7% → 2.9% (contextual embeddings + contextual BM25, −49%) → 1.9% with reranking (−67%); critics note reranking+BM25 alone reached 3.5%.

### A5. The update problem
- ChatGPT: **[secondary; openai.com returned 403]** OpenAI's June 2026 "Dreaming" post reportedly admits the old saved-memories system "often became stale and relied on users to manually manage updates", replacing it with background synthesis into an editable profile — https://openai.com/index/chatgpt-memory-dreaming/ , https://techcrunch.com/2025/04/10/openai-updates-chatgpt-to-reference-your-other-chats/ . A quoted 41.5% factual-recall figure for 2024 is **[unverified]**.
- Mem0's own blog says knowledge-update accuracy *regressed* 2.6 pts in a newer version "because of its additive design, where older facts persist alongside newer ones" — https://mem0.ai/blog/the-token-efficient-memory-algorithm-now-has-temporal-reasoning
- Zep/Graphiti uses bi-temporal edges (valid_at/invalid_at + ingestion time) — https://arxiv.org/html/2501.13956v1 — but a 2026 thirteen-configuration study found Graphiti 7.0 vs Mem0 18.0 on single-hop knowledge-update questions because "rendering superseded edges puts stale values back into the answerer's view"; prose-inline history beat versioned edges at read time (single source) — https://arxiv.org/pdf/2606.15903
- Chroma's LongMemEval slice: knowledge-update was the *easiest* category when the context is focused — the failure is retrieval surfacing the stale fact, not the model's reasoning.
- "User as Code" (2026) — https://arxiv.org/abs/2606.16707 — argues bag-of-facts memory "struggles with contradictions, aggregation, and rules because storing a fact and acting on it are separate steps"; typed executable state hits ~99% on aggregation questions where retrieval memories score 6–43%.

### A6. Compaction information loss
- **The Compaction Cliff (Aug 2026)** — https://arxiv.org/html/2608.22752v1 : on 20 real agent configs, Claude Code's /compact prompt on Sonnet 4.6 retained **53% of safety constraints after one round and 10% after five**. At 50% compression: hierarchical truncation 0.50, temporal windowing 0.58, LLMLingua-2 **0.21**, gpt-5.4-mini 0.48, Opus 4.7 0.45, vs 1.00 for a typed exact-preservation path. At 10% compression the best LLM compactor kept 0.24. LLMLingua-2 dropped a negation from a rule. Human annotators were stricter than the automatic metric (truncation 64% → 41%). Caveat: authors built the benchmark.
- **Factory.ai (16 Dec 2025)** — https://factory.ai/news/evaluating-compression : 36,000+ production messages; structured-section summary 3.70 vs Anthropic SDK compaction 3.44 vs OpenAI /compact 3.35 (0–5); all remove ~98.6–99.3% of tokens; "forcing explicit sections (files/decisions/next steps) reduces the chance that critical details silently disappear." A "37% multi-session retention" number circulating is **[secondary, unverified]**.
- **TRACE (2608.06503)** — https://arxiv.org/abs/2608.06503 : recurrent compression "weakens the influence of recent interactions" → blocked actions, repeated exploration, cross-run instability.
- **KVMem (2609.04852)** — https://arxiv.org/abs/2609.04852 : compaction "makes an early relevance decision before later needs are known"; keeping paged KV instead raised DeepSWE success 43.8% → 48.4%.
- Rate-distortion view — https://arxiv.org/abs/2607.08032 : every layer (KV eviction, prompt pruning, summarization) chooses by attention magnitude or recency, "discarding, before the query is known and irreversibly, information the query later needs"; repeated compaction "is almost never measured".
- Practitioner evidence: badlogic's survey — https://gist.github.com/badlogic/cd2ef65b0697c4dbe2d13fbecb0a0a5f — repeated compactions lose information cumulatively, mid-task auto-compaction makes agents "go off the rails"; Codex CLI itself warns users. Cursor users report ~190K → ~1K token summaries and forgotten instructions — https://forum.cursor.com/t/auto-injected-summarization-and-loss-of-context/86609 . Wang et al.'s recursive summarizer "occasionally suffers from minor factual errors" — https://arxiv.org/abs/2308.15022v2 . Taelin's spec puts it bluntly: a summary's omissions "are lost for good" — which is why his design never deletes the log.

## PART B — The techniques

### B1. Hierarchical / recursive summarization
- **RAPTOR** — https://arxiv.org/abs/2401.18059 : recursively embed → cluster → summarize into a tree; collapsed-tree retrieval over all levels. Gains are modest (NarrativeQA ROUGE-L 30.87 vs 29.26) and the clustering must be recomputed on updates — https://arxiv.org/html/2410.01736v1
- **Recursively Summarizing (Wang et al.)** — https://arxiv.org/abs/2308.15022v2 : fold each dialogue chunk into the prior memory; limitations: API cost, factual drift.
- **UniiChat / OptChat (Taelin, gist rev. 8 Oct 2026)** — https://gist.github.com/VictorTaelin/91837951a5ce5b38f341ec1ba1df6449 , product https://uniichat.com (page is onboarding only; design lives in the gist). Mechanics: append-only JSONL log of every message (tool output clipped to 30K chars, thoughts never logged); each message → ≤512-byte line; adjacent lines merge pairwise into a **binary tree** (node at level l covers 2^l messages, built once, never rebuilt); the model sees a **bounded view** of 64–128 KB covering the whole chat, fine-grained recently and coarse far back; merge order from a binary-counter "push" rule, `due = (T − last_message_of_pair) / 2^level` (measuring from the pair's *first* message is called out as a bug that churns old lines); merges happen in **batches** only when the view exceeds 128 KB (down to 64 KB), so between batches the prefix only grows at its end and prompt-cache hits are 98.6% for turns / 96.2% for compactions over a 3,000-message replay; tools `zoom(id,n)` (expand a line to its children or the full original message), `zoom("Name")`, `date(id)`; summarizer reuses the same system prompt/tools to share cache, with priority order user words ≈ verbatim > lasting effects/failures > findings > tool steps; no dates in the system prompt; nothing carries between turns. Open questions from comments: recall when unrelated topics share a window, topic scatter across branches. Ports: https://github.com/catoncat/pi-endless (~40K prompt tokens/message, 92% cache hits, ≈$8 per 1,000 messages at Haiku 4.5 prices), https://github.com/fourseven/hermes-optchat
- **Mastra Observational Memory** — https://mastra.ai/research/observational-memory : Observer converts raw messages into dated, priority-tagged bullet observations (3–6× text, 5–40× tool-heavy) and a Reflector periodically rewrites/merges them; append-only between reflections so the prefix caches; no per-turn retrieval. LongMemEval 93.27% (gemini-3-pro), 94.87% (gpt-5-mini) at ~30K average context; full-context gpt-4o 60.2%.
- **TiMem (ACL Findings 2026)** — https://aclanthology.org/2026.findings-acl.1091/ : temporal containment tree; 76.88 LongMemEval-S, recalled memory length −52%.
- **OpenHands condenser** — https://docs.openhands.dev/sdk/arch/condenser : replace the first half of events with one summary event, always keep first 2 events, re-summarize summaries, retain the full event log separately.
Weakness class: compounding loss and drift (A6), unless—as in UniiChat/OpenHands—the raw log is kept and reachable.

### B2. Prompt (token-level) compression
LLMLingua-2 — https://arxiv.org/abs/2403.12968 : 2–5× at modest loss, 3–6× faster than LLMLingua; an independent follow-up reports a 16.1-pt single-doc-QA drop going from 3× to 5× — https://arxiv.org/pdf/2503.07956 . LongLLMLingua on NaturalQuestions fell 47% from 1.53× to 3.44× and matched closed-book at 3.44× — https://arxiv.org/pdf/2406.02376 . The "20× with <2% loss" figure belongs to original LLMLingua on CoQA/HotpotQA **[secondary]**. Compaction Cliff: LLMLingua-2 kept 21% of rules and deleted negations. Verdict: fine for bulky tool output, dangerous for user statements, rules, numbers, and anything with a "not".

### B3. KV-cache compression and latent context (needs weights)
- Eviction: StreamingLLM (sinks + recent window), H2O (cumulative attention), SnapKV (observation window), PyramidKV. On reasoning tasks SnapKV/H2O dominate but H2O "still significantly lags full cache" — https://arxiv.org/pdf/2512.12008 ; multi-instruction prompts break — https://arxiv.org/abs/2510.00231
- Learned soft-token compression: Gist tokens up to 26× but instructions-only; ICAE 512 tokens → 32–128 vectors (4×, up to 16×) with a frozen decoder — https://arxiv.org/pdf/2307.06945 ; AutoCompressor ~15× summary vectors; Activation Beacon 8× KV memory, 2× speed — https://arxiv.org/pdf/2401.03462 ; xRAG one token per document but needs an extra encoder + projector — https://proceedings.neurips.cc/paper_files/paper/2024/file/c5cf13bfd3762821ef7607e63ee90075-Paper-Conference.pdf (survey: https://aclanthology.org/2025.naacl-long.368.pdf)
- **Cartridges (Hazy Research)** — https://arxiv.org/abs/2506.06266 : train a small KV cache per corpus with "self-study" (synthetic conversations + context distillation; plain next-token training does not match ICL): 38.6× less memory, 26.4× throughput, effective context 128K → 484K on MTOB, composable at inference. Cost: a training run per corpus.
- **Still (2026)** — https://arxiv.org/abs/2606.07878 : a per-layer Perceiver trained once produces compact K/V in a single forward pass, 8×–200× at 8K–128K, +8–22 on RULER vs baselines, iterable across a task — the amortized successor to Cartridges.
- **REMORY** **[secondary, HF preprint]** — https://aiweekly.co/alerts/remory-compacts-agent-context-to-52-with-soft-memory-tokens : soft memory tokens appended after a plain text summary; near full-context SummHay at 5.2% of positions.
- **KVMem** — https://arxiv.org/abs/2609.04852 : page KV across GPU/host/NVMe with attention-space indexes; 1M-token workspace on a 24 GB laptop GPU at ~50 tok/s.
API reality: none of this is reachable through Anthropic/OpenAI/Google APIs. The only latent reuse you get via API is prompt caching (opaque KV reuse of an identical prefix) and OpenAI's opaque encrypted compaction item.

### B4. Test-time training / parametric memory
- **Titans** — https://arxiv.org/html/2501.00663v1 : neural memory updated at inference by the gradient of an associative loss ("surprise"), with momentum on past surprise and a forgetting gate α; variants MAC/MAG/MAL; S-NIAH@16K MAC 98.4/97.4/95.2; claims >2M context. **Nested Learning / HOPE (Google, Nov 2025)** — https://research.google/blog/introducing-nested-learning-a-new-ml-paradigm-for-continual-learning/ , https://arxiv.org/abs/2512.24695 : Continuum Memory System with modules updating at different frequencies; self-modifying Titans variant; proof-of-concept, no weights indicated.
- **Memory Layers at Scale (Meta)** — https://arxiv.org/abs/2412.09764 : trainable key-value lookups up to 128B params beat dense models at >2× compute on factual tasks; a pretraining design, not per-user.
- **Per-user adapters:** cumulative LoRAs underperform a single evolving LoRA (ICLR 2026) — https://arxiv.org/pdf/2510.25093 ; per-user adapters share most structure, so a shared factor bank + tiny per-user code is proposed — https://arxiv.org/html/2610.02353 ; forgetting remains open (SLoRA — https://aclanthology.org/2026.acl-long.247.pdf). **Doc-to-LoRA (Sakana)** — https://pub.sakana.ai/doc-to-lora/ : hypernetwork emits a rank-8 LoRA from a document in <1 s, 83.5% of full-context SQuAD, near-perfect NIAH to ~40K on a 2B model; meta-training takes days–weeks.
- **Sleep-time compute (Letta, Apr 2025)** — https://forum.letta.com/t/sleeptime-agents-for-memory-consolidation-best-practices-guide/154 : a background agent merges/dedupes/prunes memory blocks during idle time (cheaper model recommended). Auto-Dreamer learns an offline consolidator — https://arxiv.org/pdf/2605.20616
Feasibility for a personal agent in 2026: parametric per-user memory is open-weights-only, unauditable, and cannot delete a single fact; amortized compressors (Cartridges/Still/Doc-to-LoRA) are the practical form, and only on self-hosted models.

### B5. Structured extraction / "memory as a document"
- **Mem0** — https://arxiv.org/html/2504.19413v1 : extraction LLM sees a rolling summary + last 10 messages + new pair → candidate facts; for each, retrieve top-10 similar memories and let the LLM choose ADD/UPDATE/DELETE/NOOP; graph variant marks superseded edges invalid rather than deleting. LoCoMo J: single-hop 67.13, multi-hop 51.15, temporal 55.51, open 72.93; full-context 72.90 overall but 26,031 tokens/query vs 1,764. Zep disputes the comparison — https://blog.getzep.com/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/
- **Zep/Graphiti** — https://arxiv.org/html/2501.13956v1 : bi-temporal knowledge graph; DMR 94.8 vs MemGPT 93.4; LongMemEval up to +18.5% and −90% latency vs full-context.
- **Letta core memory blocks** — https://docs.letta.com/guides/agents/architectures/memgpt : persona/human/working-state blocks always in context, edited by the agent via memory_insert/replace/rethink; archival + recall tiers.
- **Anthropic memory tool** — https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool : client-side `/memories` directory with view/create/str_replace/insert/delete/rename; the API injects "ASSUME INTERRUPTION: your context window might be reset at any moment"; recommended together with server-side compaction so "memory preserves the information that must survive summarization."
- **Claude Code CLAUDE.md** is loaded up front, everything else just-in-time via glob/grep — https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
- **Honcho** — https://docs.honcho.to/ : peer-centric representations built from derived "conclusions", a dialectic endpoint you query in natural language, cached working representations, and get_context(token budget) returning summaries + recent messages. **[unverified]** the deriver's exact extraction logic is not documented on the overview page.
- **Karpathy's LLM Wiki (Apr 2026)** — https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f (via https://github.com/akitaonrails/ai-memory/blob/main/docs/research-karpathy-llm-wiki.md): immutable raw sources, LLM-owned markdown wiki, schema file; ingest one source → touches 10–15 pages, flags contradictions; index.md + append-only log.md; periodic lint; no vector DB needed to ~100 sources.
- **User as Code** — https://arxiv.org/abs/2606.16707 : typed Python state + rule functions, append-only fact log checkpointed into code; LoCoMo 78.8%; rules fire proactively on state change.
Weakness: extraction misses nuance and affect, additive stores accumulate stale facts, rigid schemas resist new fact types.

### B6. Agentic vs automatic memory
Agentic (Anthropic memory tool, Letta/MemGPT, A-MEM — https://arxiv.org/pdf/2502.12110 with 85–93% fewer memory tokens but 5,882 notes for 10 conversations — https://arxiv.org/pdf/2602.07885 ; Hindsight retain/recall/reflect, 91.4% LongMemEval with Gemini 3 Pro, 83.6% with a 20B open model — https://aclanthology.org/2026.acl-demo.27/): the model decides what to save/search, so memory is explainable and task-aware, but quality depends entirely on the model's judgment, it spends turns on bookkeeping (Letta's leaderboard penalizes extraneous memory ops), and it forgets to write. Automatic (Mem0, ChatGPT/Claude background synthesis): consistent, cheap per turn, cache-friendly, but cannot judge salience in context and tends to be additive. The two vendors have converged on background consolidation (OpenAI "Dreaming", June 2026; Claude's categorized memory entries, July 2026 **[secondary]** — https://www.memorylake.ai/en/blogs/claude-new-memory-entries).

### B7. Retrieval improvements — what matters for conversational memory
Ranked by evidence for chat memory: (1) **timestamps + time-aware query expansion + temporal filters** (LongMemEval; Mem0's 55 vs OpenAI's 22 on temporal); (2) **hybrid lexical + dense** for exact names/entities (Taelin's `search` is exact-name only; Hindsight combines vector + keyword + graph + temporal; the 11-system harness study found *no* coding agent uses embeddings, only deterministic retrieval — https://arxiv.org/abs/2609.00006); (3) **reranking**, ideally reasoning-aware (MemReranker — https://arxiv.org/pdf/2605.06132 ; Anthropic −67% with reranker); (4) **contextualizing chunks** before embedding (Anthropic contextual retrieval; Jina late chunking +1.9 abs / +3.6% rel, with the caveat that model choice matters more — https://arxiv.org/pdf/2409.04701); (5) **recency × importance × relevance** (Generative Agents: recency decay 0.995 per hour, LLM-rated importance 1–10, min-max normalized sum — https://arxiv.org/pdf/2304.03442 ; reference-code weights 0.5/3.0/2.0 are **[secondary]**); (6) multi-hop graph traversal for "who/what connects" questions (Zep, Mem0ᵍ +2%); (7) ColBERT late interaction helps on reasoning-heavy retrieval (BRIGHT 19.61 vs 12.31 **[secondary]**) at ~10× index cost — https://hamel.dev/notes/llm/rag/p4_late_interaction.html

### B8. Coding-agent compaction as a case study
- **Claude Code** — https://barazany.dev/blog/claude-codes-compaction-engine , https://gist.github.com/AtlantisPleb/1dbe12a0bc8c668efe1f79c614d36400 , https://gist.github.com/badlogic/cd2ef65b0697c4dbe2d13fbecb0a0a5f : tier 1 clears old tool results before every call (keeps 5 most recent; uses server `cache_edits` so the cached prefix survives); tier 2 server-side clearing; tier 3 full summary at ~95% capacity with a scratchpad then nine sections: Primary Request and Intent, Key Technical Concepts, Files and Code Sections, Errors and fixes, Problem Solving, All user messages, Pending Tasks, Current Work, Optional Next Step — weighted toward the most recent messages, code snippets verbatim, no tool calls allowed. After compaction it restores the 5 most recently read files (≤50K tokens), CLAUDE.md, skills, tool defs. The summarizer reuses the main system prompt + tools because a different system prompt gave a 98% cache-miss rate. Keeps: user intent and all user messages, decisions, errors, pending work. Drops: tool outputs, intermediate reasoning, anything the summarizer deems redundant — which per Compaction Cliff is ~half of constraints per round.
- **Codex CLI**: "context checkpoint" prompt; keeps ~20K tokens of recent user messages verbatim, replaces everything else; thresholds ~180K/244K.
- **OpenCode**: prunes tool outputs older than the last 40K tokens before compacting; summary is declared "the only context going forward."
- **Amp**: no auto-compaction; handoff (goal-directed extraction), fork, thread references.
- **Cline**: LLM summary on some models, else middle truncation in pairs keeping the first exchange (half or three-quarters removed) — https://github.com/cline/cline/issues/4389
- **Cursor**: summarizes oldest messages; users report ~190K → ~1K — https://docs.cursor.com/agent/chat/summarization
- **OpenAI Responses API compaction** — https://developers.openai.com/api/docs/guides/compaction : server-side at `compact_threshold` (200K in examples) or standalone `/responses/compact`; returns an **opaque encrypted compaction item** that "carries forward key prior state and reasoning"; items before it may be dropped; not human-inspectable.
- **Anthropic context editing** — https://platform.claude.com/docs/en/build-with-claude/context-editing : `clear_tool_uses_20250919` (default trigger 100K input tokens, keep 3 tool uses, `exclude_tools`, `clear_at_least` to amortize the cache-write cost); `clear_thinking_20251015`; server-side `compact_20260112` is now the primary strategy (150K trigger **[secondary, cookbook]**); client-side SDK compaction (5 sections: Task Overview, Current State, Important Discoveries, Next Steps, Context to Preserve) is deprecated.

### B9. Anthropic and Manus rules (concrete)
Anthropic — https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents : context is a finite "attention budget" with n² pairwise cost; find the smallest high-signal token set; system prompt at the "right altitude" (no brittle if-else, no vague guidance); minimal non-overlapping tool set; few diverse canonical examples over exhaustive rules; prefer just-in-time retrieval via lightweight identifiers (paths, queries) and progressive disclosure; compaction should keep architectural decisions, unresolved bugs, implementation details and drop redundant tool outputs — tune for recall first, then precision; use tool-result clearing as light-touch compaction; structured note-taking outside the window (NOTES.md, todo lists, memory tool); sub-agents burn tens of thousands of tokens but return 1–2K-token summaries.
Manus — https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus : KV-cache hit rate is the #1 metric (100:1 input:output, 10× cached discount); stable prefix (no timestamps in the system prompt); append-only, never edit earlier actions; deterministic JSON serialization; explicit cache breakpoints; mask tool logits instead of removing tools (removal invalidates cache and leaves dangling references); consistent tool-name prefixes for masking; file system as unlimited restorable memory — compression must be restorable (keep the URL/path when dropping the content); recite goals via todo.md rewritten every step (~50 tool calls/task) to pull objectives into the recent end; keep failures and stack traces in context; avoid few-shot ruts by injecting controlled variation.

### B10. 2026 "novel" ideas worth combining
UniiChat's **lossless log + bounded multi-resolution view + zoom** (B1); Karpathy's **wiki with lint and append-only log**; **git-versioned memory** (GitOfThoughts arXiv 2606.14470, Git Context Controller arXiv 2508.00031, git-backed wiki https://github.com/akitaonrails/ai-memory) — diffs give free provenance and rollback; **episodic reconstruction** (E-mem ICML 2026 keeps uncompressed episodes in helper agents — https://icml.cc/virtual/2026/poster/65274 ; EM-LLM surprise-segmented episodes — https://proceedings.iclr.cc/paper_files/paper/2025/file/c05144b635df16ac9bbf8246bbbd55ca-Paper-Conference.pdf ; MemRL learns what to write); **dual-process fast/slow** (Mastra Observer/Reflector, Letta sleep-time, OpenAI Dreaming, Auto-Dreamer); **typed compaction** routing constraints/preferences through an exact-preservation path (TypeCompact); **executable user models** (User as Code) and **Bayesian belief updating** about preferences (LLMs don't update beliefs with more evidence by default; fine-tuning toward a Bayesian assistant fixes it — https://arxiv.org/pdf/2503.17523v3 , Nature Comms Jan 2026); **diff-based updates** (Taelin: "an old line changes only when its content does"; User-as-Code append-only log checkpointed to typed state); **soft memory tokens beside text summaries** (REMORY). **[unverified]** No controlled study of "narrative/story-form summaries retain more than bullet facts" was found; the available evidence (MemMachine — https://arxiv.org/pdf/2604.04853 ; Factory) points the other way: structured/event records beat prose for factual and temporal recall.

| Technique | Compresses what | Lossy? | API or weights? | Best for | Weakness |
|---|---|---|---|---|---|
| Rolling/recursive summary (Wang; Codex/Claude Code compaction) | Whole history → prose | Yes, compounding (≈50% of constraints/round) | API | Task continuity in one session | Drift, drops rules/negations/numbers, irreversible |
| Multi-resolution tree + zoom (UniiChat/OptChat) | History → ≤512-B lines, binary tree, 64–128 KB view | View lossy; log lossless | API (cache-aware) | Endless personal chat, constant cost, 98% cache hits | Latent recall across scattered topics; summarizer quality; zoom costs turns |
| Observer/Reflector observations (Mastra OM) | Messages → dated bullet observations | Yes (3–40×) but reflected, not truncated | API | Cache-friendly long sessions, 93–95% LongMemEval | Reflection rewrites invalidate cache; multi-session ceiling ~87% |
| RAPTOR / TiMem trees | Corpus/history → clustered summaries | Yes | API | Thematic/holistic questions | Rebuild on updates; modest gains |
| LLMLingua-2 token pruning | Any text, 2–5× | Yes; kills negations | API | Bulky tool output | 21% rule retention; 16-pt QA drop at 5× |
| Tool-result clearing (Anthropic context editing; Claude Code tier 1; OpenCode) | Old tool outputs → placeholder | Yes, but restorable if path/URL kept | API | Agent loops | Nothing for user statements |
| OpenAI encrypted compaction item | Full window → opaque item | Yes (unknown) | API only, opaque | Responses-API agents | Uninspectable, unauditable |

| Cartridges / Still / Doc-to-LoRA | Corpus → tiny KV or LoRA (38×–200×) | Low (matches ICL) | Weights + training | Stable corpora (your archive of past months) | Per-corpus training; not updatable per message |
| Soft memory tokens (ICAE/Beacon/REMORY) | Text → vectors 4–16× | Low–moderate | Weights | Side-channel next to a text summary | Training; opaque |
| Titans/HOPE test-time memory | Context → weights online | Unknown | New architectures | Research | No deployable weights |
| Per-user LoRA / sleep fine-tune | History → weights | Yes, unauditable | Weights | Style/preference priors | Forgetting, can't delete a fact, stacking hurts |

| Rewritable documents (CLAUDE.md, Letta blocks, memory tool, Karpathy wiki) | Knowledge → curated pages | Yes (curation) | API | Stable user model, always-in-context identity | Depends on model discipline; bloat; contradictions need lint |
| Executable user model (User as Code) | Facts → typed state + rules | Low for typed facts | API | Aggregation, contradictions, proactive alerts | Schema design; untyped nuance lost |
| Hybrid BM25+dense + time filters + rerank | Nothing (retrieval) | n/a | API | "Last Tuesday", exact names | Negation; embedding granularity |
| Contextual retrieval / late chunking | Chunk → chunk+context embedding | n/a | API | Cross-session chunks | +1.9–3 pts only; cost of context generation |
| Recency×importance×relevance (Generative Agents) | Scoring, not storage | n/a | API | Salience in chat memory | Hand-tuned weights |
| Episodic replay (E-mem/EM-LLM) | Keeps raw episodes, reconstructs | No | API (multi-agent) / weights | High-fidelity recall of specific events | Cost; coordination |
| Sleep-time consolidation (Letta, Dreaming) | Memory store → merged/pruned store | Yes | API | Background dedupe/update | Extra cost; may erase |
| Git-versioned memory | Snapshots + diffs | No | API | Provenance, rollback, "what changed" | Needs the model to read diffs |
| Typed compaction (TypeCompact) | Routes constraints to exact path | No for typed class | API | Safety rules, hard preferences | Classifier recall bound (0.93) |

**Design implication from the evidence:** keep an immutable, timestamped log; never let the model's working view exceed the ~16K-token latent-recall regime for the parts it must reason over; make every compression restorable (zoom/paths/diffs); route typed facts (preferences, constraints, life-state with valid-from/valid-to) through exact-preservation, not summarization; retrieve with time filters + lexical + rerank rather than dense-only; and keep the prefix append-only and batch-rewritten so the cache does the heavy lifting.
